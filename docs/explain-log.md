# 説明ログ(プレゼミ生への説明用)

## 段階:テストツール vitest の導入と ERESOLVE(依存関係の衝突)の解決

### 作ったもの
- テストを実行するための道具 `vitest` を、プロジェクトに追加した。
- あわせて `@types/node` を 20 系から 24 系に更新した。
- 変更されたファイル:`package.json`、`package-lock.json`

### 使った技術
- npm(Node.js のパッケージ管理ツール)
- vitest 5.0.4(テストフレームワーク)
- @types/node 24.19.2(Node.js の型定義)

### なぜそうしたか
最初に `npm install -D vitest` を実行したところ、`ERESOLVE` というエラーで止まった。

**何がぶつかったか**

| 部品 | 求めているもの |
|---|---|
| このプロジェクト | `@types/node` は 20 系(`^20`) |
| vitest 5.0.4 | `@types/node` は 22 系、または 24 以上(`^22.0.0 \|\| >=24.0.0`) |

プロジェクトは「20 系を使う」と書いているのに、vitest は「20 系は困る」と言っている。npm は、どちらを優先するか自分では決められないので、止まってエラーを出した。

**解決方法**
1. 自分の PC の Node.js は v24.16.0 なので、型定義も同じ 24 系に揃えるのが自然だと判断した。
2. 先に `npm install -D @types/node@24` で型定義を 24 系に上げた。
3. そのあとに `npm install -D vitest` を実行した。今度は衝突せず、そのまま入った。

**やらなかったこと**
`--force` や `--legacy-peer-deps` を付ければ、エラーを無視して入れることはできる。ただし、食い違いを抱えたまま動かすことになり、あとで原因の分かりにくい不具合が出るおそれがある。そのため、食い違いそのものを直す方法を選んだ。

### 確認方法
cmd で次の 2 つを実行する。

```
npm ls vitest @types/node
npx tsc --noEmit
```

- 1 つ目:`vitest@5.0.4` と `@types/node@24.19.2` が表示され、`invalid` や `UNMET` が出ないこと。
- 2 つ目:何も表示されずに終わること(型エラーが 0 件)。

実際の結果:どちらも問題なし。

### 初出の専門用語と一言解説
- **ERESOLVE**:npm が「依存関係をどう組み合わせても、条件を満たせない」と判断したときのエラー名。
- **依存関係(dependency)**:あるパッケージが動くために必要な、別のパッケージのこと。
- **peer dependency(ピア依存)**:「このバージョンの部品と一緒に使ってね」と、パッケージが利用者側に求める条件。
- **vitest**:テストを書いて実行するための道具。順位計算が正しいかを自動で確かめるのに使う。
- **@types/node**:TypeScript に Node.js の機能を教えるための型定義。
- **devDependencies(`-D`)**:開発中だけ使い、本番では使わない部品の置き場所。
- **package-lock.json**:実際に入ったバージョンを記録するファイル。誰が入れても同じ構成になる。
- **`tsc --noEmit`**:TypeScript の型チェックだけを行い、ファイルは出力しないコマンド。

## 段階1:順位計算 `lib/ranking.ts` とテスト

### 作ったもの
- `lib/ranking.ts`:順位を計算する 2 つの関数。
  - `computeRanking(videos, votes)`:動画と票から、順位つきの一覧を作る。
  - `filterByRevealStage(ranking, stage)`:発表段階(0〜3)で見せてよい順位だけを取り出す。
- `lib/ranking.test.ts`:上の関数が正しいかを確かめる自動テスト 20 件。
- `vitest.config.mts`:テストの設定(`lib/` 内の `*.test.ts` を対象にする)。
- `package.json` に `test` スクリプトを追加(`npm test` でテストを実行)。

### 使った技術
- TypeScript(型つきの JavaScript)
- Vitest(テストツール)

### なぜそうしたか
- **純粋関数にした**:DB も画面も使わず、「入力を渡せば結果が返る」だけの形にした。DB がなくても、テストだけで正しさを確かめられるため。
- **最初に作った**:この関数がシステムの核心(ルールそのもの)で、ほかの部分はこれを呼ぶだけになるため。
- **平均の比較は割り算せず、整数で比べた**:`1/3` のような割り切れない平均は、小数にすると誤差が出て「同点のはずが同点にならない」ことがある。合計と件数の整数どうしを掛け算で比べれば、誤差が出ない。
- **同順位は標準競技順位(1,2,2,4)**:同順位が 2 人いたら、次は 3 位ではなく 4 位にする。
- **段階の絞り込みも関数にした**:見せてはいけない順位を「画面で隠す」のではなく、「関数が返さない」ようにするため。API はこの関数の結果をそのまま返せばよい。
- **3 位が存在しない場合**:該当者のいない順位は、空の一覧を持つ順位として返す。画面側が「該当者なし(同順位のため3位はいません)」と表示する。

### 確認方法
cmd で次を実行する。

```
npm test
```

`Tests 20 passed (20)` と表示されれば成功。型チェックは `npx tsc --noEmit`(何も表示されなければ成功)。

### テストが確かめていること
| 区分 | 確かめていること |
|---|---|
| 自己投票 | 自分の動画への票は集計されない / 自己投票しかない動画は順位に出ない |
| 欠席者 | 票が 1 票の動画と 3 票の動画で、合計ではなく平均で順位が決まる |
| not_shown | 放映できなかった動画は、票があっても順位に出ず、他の順位も変わらない |
| 投票なし | 投票が 1 件もない動画は順位に出ない / 票が 0 件なら空の結果 |
| 同点 | 総合点が同じならインパクト平均が高い方が上 / 完全な同点は同順位で次が飛ぶ(1,2,2,4) / 割り切れない平均でも誤差で同点が崩れない |
| 再投票 | 同じ人が同じ動画に投票し直すと新しい内容に上書きされる(順番が逆でも日時が新しい方が残る) |
| 発表段階 | 段階0は空 / 1は3位だけ / 2は3位と2位 / 3は3位・2位・1位 / 隠すべき順位が結果のどこにも含まれない / 同順位や 3 人未満では空の順位になる / 0〜3 以外はエラー |

### 初出の専門用語と一言解説
- **純粋関数**:同じ入力なら必ず同じ結果を返し、外の状態を変えない関数。電卓のようなもの。
- **ユニットテスト(単体テスト)**:小さな部品ひとつひとつを、自動で確かめるテスト。
- **標準競技順位**:同順位が出たら、その人数分だけ次の順位を飛ばす数え方(1,2,2,4)。
- **スクリプト(`scripts`)**:`package.json` に書く、コマンドの短縮名。`npm test` は `vitest run` の短縮。

## 段階2:データベースの設計図(SQL)を作る【まだ実行していない】

### 作ったもの
- `supabase/schema.sql`:テーブル 4 つ(members / videos / votes / app_state)、制約、RLS の設定。
- `supabase/seed.sql`:初期データ(名簿 10 名、動画 10 本、アプリ状態 1 行)。
- `supabase/verify.sql`:わざと不正なデータを入れて、DB が弾くかを確かめる検証。終わったら全部取り消す。

### 使った技術
- PostgreSQL(Supabase の中身のデータベース)と、その操作言語 SQL

### なぜそうしたか
- **ルールを DB にも書いた**:画面や API のチェックをすり抜けても、DB が最後に止める。自己投票・点数の範囲・open は 1 本だけ、はすべて DB の制約にした。
- **トークンは DB が作る**:`gen_random_uuid()` を 2 つつなげた 64 文字。値は SQL ファイルのどこにも書かれないので、Git にも会話にも出ない。
- **名簿は seed.sql だけで差し替え**:名前や ID はコードに書かない。動画の行は名簿から自動で作る。
- **RLS を有効にし、ポリシーは作らない**:公開キーでは何も読み書きできない。さらに保険として、公開キー系の役割(anon / authenticated)の権限そのものも取り上げた。
- **begin ... commit で囲んだ**:途中で失敗したら、全部なかったことになる。中途半端な状態が残らない。
- **verify.sql は begin ... rollback で囲んだ**:検証用データは最後に取り消されるので、本番データを汚さない。

### 確認方法
(実行は承認後。手順は下の「Supabase の画面での実行手順」を参照)
1. `schema.sql` を実行 → 「Success. No rows returned」と出る。
2. `seed.sql` を実行 → 表に `members=10, videos=10, min_token_length=64, reveal_stage=0` と出る。
3. `verify.sql` を実行 → 赤いエラーが出ず、最後の表で `verify_leftover=0, votes=0` と出る。

実行前の確認として、使い捨てのメモリ上の PostgreSQL(PGlite)で 3 つのファイルを通し、すべて成功することを確かめた。また、制約をわざと外した状態で verify.sql を流すと、`NG:` で止まる(検証が効いている)ことも確かめた。ただし本物の Supabase ではまだ実行していない。

### テーブルと制約の対応表
| テーブル | 制約 | 守っていること |
|---|---|---|
| members | 主キー id、token は一意、token は 32 文字以上 | 学籍番号の重複なし、トークンの重複・短すぎる値なし |
| videos | 主キー member_id、status は 4 種類のみ、部分ユニークインデックス | 1 人 1 本、不正な状態なし、open は同時に 1 本 |
| votes | 主キー (voter_id, target_id)、voter_id <> target_id、tech / impact は 1〜5 | 1 人 1 動画 1 票(再投票は上書き)、自己投票なし、点数の範囲 |
| app_state | id = 1 のみ、reveal_stage は 0〜3 | 行は最大 1 つ、発表段階の範囲 |

なお「投票を受け付けるのは status='open' の動画だけ」は、DB ではなく API(段階4)で守る。

### Supabase の画面での実行手順(画面の名称は変更されることがある)
> ※この手順は、次の「段階2(方式変更)」の節で置き換えた。新しいプロジェクトは作らず、既存プロジェクトの中に専用スキーマを作る。実際に行うのは、次の節の手順のほう。

1. ブラウザで supabase.com を開き、「Start your project」からサインイン(GitHub またはメール)。
2. 「New project」を押す。Organization を選び、Name に `seminar-vote` などを入力。
3. 「Database Password」は「Generate a password」で作り、パスワード管理ツールに保存する(会話には貼らない)。
4. 「Region」は「Northeast Asia (Tokyo)」を選び、「Create new project」を押す。数分待つ。
5. 左のメニューの「SQL Editor」(`>_` のアイコン)を開き、「New query」を押す。
6. VS Code などで `supabase/schema.sql` を開いて全文コピー → エディタに貼り付け → 右下の「Run」(または Ctrl+Enter)。「Success. No rows returned」と出れば成功。
7. 左のメニューの「Table Editor」を開き、4 つのテーブルがあることを確認する。
8. 「SQL Editor」で「New query」→ `seed.sql` を貼り付けて「Run」。結果の表に `members=10` などが出れば成功。
9. もう一度「New query」→ `verify.sql` を貼り付けて「Run」。赤いエラーが出ず、最後の表で `verify_leftover=0` なら合格。`NG:` で始まるエラーが出たら不合格。
10. 失敗したら、画面のエラーメッセージをそのまま教える(トークンやキーは貼らない)。

**【注意】SQL がエラーで止まったとき**
1. まず、新しいクエリに `rollback;` と **1行だけ**書いて実行する。
2. エラーメッセージを読んで原因を直す。
3. そのあとで、もとの SQL を最初から再実行する。

なぜ必要か:`schema.sql` と `seed.sql` は `begin;`(ここから 1 かたまり)で始まり、`commit;`(確定)で終わる。途中でエラーが出ると、`commit;` まで届かず、「かたまりを開いたまま、中断した状態」で止まることがある。この状態の接続では、次に実行するものが `current transaction is aborted` というエラーで拒否される。`rollback;` は「このかたまりを取り消して閉じる」という命令で、実行すると接続が元の状態に戻り、次の SQL が通るようになる。
データは `begin;` ... `commit;` のおかげで、エラーの時点で確定されていない。そのため `rollback;` を実行しても失うものはない。
たとえるなら、ノートに下書き(begin)をしている途中で間違いに気づいたとき、下書きを破って(rollback)から、白紙で書き直すイメージ。

`verify.sql` も同じ。`NG:` というエラーで止まったときは、同様に `rollback;` を実行する。

### 初出の専門用語と一言解説
- **テーブル**:表のこと。1 行が 1 件のデータ。
- **主キー(PRIMARY KEY)**:1 行を見分けるための列。重複できない。
- **外部キー(REFERENCES)**:「別の表に実在するものだけ入れてよい」という約束。
- **CHECK 制約**:入れてよい値の条件。改札機のようなもの。
- **部分ユニークインデックス**:「条件に合う行の中だけ」重複を禁止する仕組み。ここでは「open の行は 1 本だけ」。
- **RLS(行レベルセキュリティ)**:行ごとに読み書きを制限する鍵。ポリシーが無いと誰も通れない。
- **ポリシー**:RLS の「通してよい条件」の書き方。今回は作らない。
- **service_role / anon**:Supabase の役割。service_role はサーバー専用の万能キー、anon は公開キーで権限が小さい。
- **トランザクション(begin / commit / rollback)**:複数の操作を「全部成功か、全部なかったことか」にまとめる仕組み。rollback は取り消し。
- **gen_random_uuid()**:推測できないランダムな ID を作る DB の関数。
- **シード(seed)**:最初に入れておく初期データ。

## 段階2(方式変更):既存プロジェクトの中に専用スキーマ seminar_vote を作る【まだ実行していない】

### 変えた理由(無料枠の制限)
Supabase の無料プランでは、作れるプロジェクトの数に上限がある。その枠がすでに埋まっていて、このアプリのために新しいプロジェクトを作れない。
そこで、すでにあるプロジェクト(減量アプリが使っている)の中に、このアプリ専用の「引き出し」(スキーマ)`seminar_vote` を作る方式にした。

### スキーマとは(たとえ話)
1 つのデータベースを「大きな戸棚」とすると、スキーマは「引き出し」。テーブル(表)は引き出しの中の書類にあたる。
減量アプリの書類は `public` という引き出しに入っている。このアプリの書類は `seminar_vote` という別の引き出しに入れる。
引き出しが違えば、同じ名前の書類(たとえば `members`)があっても混ざらない。

### 変えたもの
| ファイル | 変更内容 |
|---|---|
| `supabase/schema.sql` | `create schema seminar_vote;` から始め、すべての名前に `seminar_vote.` を付けた。権限は service_role にだけ渡す。 |
| `supabase/seed.sql` / `supabase/verify.sql` | すべて `seminar_vote.` 付きに変更。verify には権限の確認(テスト 14〜16)を追加。 |
| `supabase/precheck.sql`(新規) | 実行前の確認用。読み取り専用で、変更は何もしない。見るのは「`seminar_vote` が未使用か」と「必要なロール(`anon` / `authenticated` / `service_role`)があるか」の 2 点だけ。`public` など他のスキーマの中身は読まない。 |
| `supabase/teardown.sql`(新規) | 後片づけ用。`drop schema seminar_vote cascade;` のみ。**今は実行しない。** |

### 権限の考え方
- **service_role にだけ**、スキーマへの入室(usage)と、4 つのテーブルの読む・追加・更新・削除(select / insert / update / delete)を渡す。
- **anon・authenticated・public(全員を表す特別な名前)には何も渡さない**。RLS を有効にし、ポリシーも作らないので、二重に鍵がかかる。
- 権限の文は、`seminar_vote` のスキーマ名とテーブル名を 1 つずつ書いて指定した。「public スキーマのテーブル全部」のような広い範囲の文は 1 つも使っていない(検索でも確認済み)。
- ※ `from public, anon, authenticated` の `public` は「全員」を表す特別な名前で、`public` スキーマ(減量アプリの引き出し)とは別物。

### リスクと対策
| リスク | 対策 |
|---|---|
| 減量アプリの `public` を壊してしまう | すべての名前に `seminar_vote.` を付ける。広い範囲を指定する文は使わない。実行前に `precheck.sql` で「`seminar_vote` が未使用か」を確認する(`public` の中身は読まない)。実行前に使い捨ての DB で、`public` が一切変わらないことを確認済み。 |
| 秘密キーは「プロジェクト全体に届くキー」なので、漏れると減量アプリのデータにも届く | キーは `.env.local` と Vercel の環境変数にだけ置く。ブラウザ・Git・会話には出さない。コードでは `schema: 'seminar_vote'` を固定し、`public` を参照するコードは書かない。公開前(段階 10)に漏れがないか確認する。詳しくは次の「キーの影響範囲」の表を参照。 |
| コードでスキーマ指定を忘れると、同名の `public.members`(減量アプリ)を読んでしまう | 接続部品(`lib/supabase.ts`)で、スキーマを `seminar_vote` に固定する(次の「段階 3 での方針」を参照)。 |
| Data API の設定を間違えて、減量アプリが動かなくなる | 「Exposed schemas」には `seminar_vote` を**追加するだけ**にして、既存の項目は消さない。変更前の画面をメモ(スクリーンショット)しておく。 |
| 無料枠の容量・接続数を減量アプリと共有する | このアプリのデータは数十行で、10 人が 2〜3 秒おきに確認する程度。負荷は小さい。 |
| 無料プランでは自動バックアップがない場合がある | 心配なら、実行前に減量アプリ側のデータを書き出しておく(するかどうかはあなたの判断)。 |
| 使い終わったあとにデータが残る | `teardown.sql` で `seminar_vote` だけを丸ごと消せる。10/22 の後に、あなたの判断で実行する。 |

### キーの影響範囲
このアプリは、サーバー専用の秘密キー(新しい形式の `sb_secret_…` キー)を使う。環境変数の名前は `SUPABASE_SERVICE_ROLE_KEY` から **`SUPABASE_SECRET_KEY`** に変更した(`.env.local` と Vercel の両方で、この名前にそろえる)。

| 項目 | 内容 |
|---|---|
| 専用の secret key を作っても権限は変わらない | 権限は `service_role` と同じ。**減量アプリの `public` にも届く。** 「専用のキー」にしても、アクセスできる範囲が狭くなるわけではない。 |
| 範囲を守っているのは何か | キーではなく、**コードの書き方**。接続部品で `schema: 'seminar_vote'` を固定し、`public` を参照するコードを書かないこと。 |
| 専用キーの利点 | **このアプリのキーだけを、10/22 の後に単独で削除できる。** 減量アプリが使っているキーには影響しない。 |
| 削除するときの注意 | 削除は**取り消せない**。先に、「そのキーを使っている別のものが無い」「代わりのキーが不要である」ことを確認してから行う。 |
| 扱い方 | `.env.local` と Vercel の環境変数にだけ置く。ブラウザ・Git・会話には出さない。 |

### Supabase の画面での手順(画面の名称は変更されることがある)
実行前に、毎回私に声をかけてください(DB の変更にあたるため)。
1. **precheck(確認)**
   1. 既存のプロジェクトを開く。左のメニューの「SQL Editor」(`>_` のアイコン)→「New query」。
   2. `supabase/precheck.sql` を全文コピーして貼り付け、「Run」を押す。
   3. 表を目で確認する。
      - `seminar_vote の状態` の行が「**未使用(OK)**」になっている。
      - (`public` など他のスキーマの中身は、この確認では読まない。)
      - `ロール` の行に `anon` / `authenticated` / `service_role` の 3 つがある。
   4. 「【注意】すでに存在する」と出たら、ここで止まって教える。
2. **schema(スキーマとテーブルを作る)**:「New query」→ `supabase/schema.sql` を貼り付けて「Run」。「Success. No rows returned」なら成功。
3. **seed(初期データを入れる)**:「New query」→ `supabase/seed.sql` を貼り付けて「Run」。結果の表に `members=10, videos=10, min_token_length=64, reveal_stage=0` と出れば成功。
4. **verify(検証)**:「New query」→ `supabase/verify.sql` を貼り付けて「Run」。赤いエラーが出ず、最後の表で `verify_leftover=0, votes=0` なら合格。`NG:` が出たら不合格。
5. **Data API に seminar_vote を公開する**(アプリのサーバーが `seminar_vote` を読み書きするために必要)
   1. 左下の「Project Settings」(歯車)→「Data API」(古い画面では「API」)を開く。
   2. 「Exposed schemas」の欄を見つける。**今ある項目(`public` など)は消さない。**変更前の画面をメモしておく。
   3. その欄に `seminar_vote` を**追加**して、「Save」を押す。
6. エラーで止まったときは、先に `rollback;` を 1 行だけ実行してから、原因を直して再実行する(前の節の【注意】を参照)。

### 段階 3 での方針(接続部品 `lib/supabase.ts`)
段階 3 で作る接続部品では、次の 2 点を必ず指定する。
- `db: { schema: 'seminar_vote' }`:何も指定しなくても `seminar_vote` の表を使うようにして、`public` を読む事故を防ぐ。
- `auth: { persistSession: false }`:サーバー側で、ログイン状態を保存しない(キーだけで動かす)。

**`sb_secret_` キーと `@supabase/supabase-js` の対応(ソースコードを読んで確認。Supabase にはまだ接続していない)**

### 初出の専門用語と一言解説
- **スキーマ(schema)**:データベースの中の「引き出し」。同じ名前のテーブルでも、引き出しが違えば別物。

- **Data API / Exposed schemas**:アプリのサーバーが Supabase の表にアクセスするための窓口と、そこから見せてよい引き出しの一覧。
- **drop schema ... cascade**:引き出しを、中のテーブルごと完全に削除する命令。元に戻せない。
- **読み取り専用(read only)**:見るだけで、書き込みができない状態。precheck がこれにあたる。

## 段階4:投票用の API(画面はまだ無い)

### 作ったもの
- `app/api/vote/route.ts`:画面から呼ぶ窓口(Route Handler)。
  - `GET /api/vote` … 本人確認と、いまの状態(投票中の動画・自分の動画か・送信済みの内容)を返す。
  - `POST /api/vote` … 投票を送信する(送信済みなら上書き)。
- `lib/vote-api.ts`:判断のロジック(入力チェック、自己投票の拒否、投票中かの確認など)。DB には直接触らない。
- `lib/vote-repo.ts`:DB への本物の窓口(Supabase の `seminar_vote` に読み書きする)。
- テスト:`lib/vote-api.test.ts`(判断ロジック)、`lib/vote-repo.test.ts`(問い合わせの書き方)、`lib/vote-route.test.ts`(HTTP としての見た目)。

### 使った技術
- Next.js の Route Handler(Web 標準の `Request` / `Response`)
- Supabase(PostgREST 経由)と Vitest(偽物の窓口でのテスト)

### なぜそうしたか
- **判断と DB を分けた**:「判断のロジック」は、DB の窓口(`VoteRepo`)だけを通して動く。テストでは窓口を偽物に差し替えるので、本物の DB なしで、締切後・自己投票などの場面を何度でも再現できる。
- **トークンはヘッダーで受け取る**(`x-vote-token`):URL に入れると、アクセスログや共有リンクに残りやすい。クエリ(`?token=`)に付けても無視する。
- **投票先はサーバーが決める**:クライアントからは「どの動画に投票するつもりか」(`targetId`)も送らせる。サーバーは「いま open の動画」を自分で調べ、一致しなければ拒否する。これは信用しないためだけでなく、**管理者が動画を切り替えた瞬間に押された投票が、次の動画に入ってしまう事故**を防ぐため。
- **自己投票は API でも拒否**(4 か所の防御のうち、画面・DB・集計に加えて、API の分):DB の CHECK 制約より前に、わかりやすい日本語で断る。
- **点数は 1〜5 の整数だけ**:`3.5`、`"3"`(文字列)、`null`、`true`、範囲外はすべて拒否。
- **不正なトークンは同じ返事**:「形式が違う」と「存在しない」を区別しない(どちらも 401・同じ文)。区別できると、トークンを当てずっぽうで探る手がかりになる。形式違いのときは、DB にも問い合わせない。
- **本文の `voterId` は無視**:投票者はトークンだけで決める。
- **DB のエラーは中身を見せない**:利用者には「少し待ってからもう一度」だけ見せ、詳しい内容はサーバーのログにだけ残す。
- **キャッシュしない**:このプロジェクトは `cacheComponents` が有効。付属のドキュメントを読んで、`export const dynamic = 'force-dynamic'` は付けず、リクエストのヘッダーを読む作りにした(読むだけで、毎回リクエストのたびに実行される)。念のため、全ての返事に `Cache-Control: no-store` を付けた。ビルドの結果でも `/api/vote` は `ƒ (Dynamic)`(毎回実行)と表示された。

### 返事の種類(HTTP ステータスコード)
| コード | 意味 | 例 |
|---|---|---|
| 200 | 成功 | 状態の取得、投票の保存 |
| 400 | 送られた内容が正しくない | 点数が 6、本文が壊れている |
| 401 | 本人確認できない | トークンが無い・形式が違う・存在しない |
| 403 | 許されない操作 | 自分の動画への投票 |
| 409 | いまの状態と合わない | 投票中の動画が無い(未放映・締切後)、動画が切り替わった |
| 500 | サーバー側の問題 | DB の障害など |

### 失敗から学んだこと:偽物の窓口では見つからず、本物の DB で初めて分かった
**起きたこと**:ユニットテストはすべて通ったのに、本物の DB で通し確認をすると、投票中の動画を調べる処理が `500` になった。サーバーのログには次の 1 行があった。

```
PGRST201 Could not embed because more than one relationship was found for 'videos' and 'members'
```

**原因**:投票中の動画の「持ち主の名前」を、1 回の問い合わせでまとめて取るために、`videos` の中に `members` を埋め込む書き方(`members(name, name_en)`)をした。ところが `videos` と `members` をつなぐ道が 2 本あった。
1. 直接の道:`videos.member_id` → `members.id`(外部キー)
2. 遠回りの道:`videos` → `votes`(投票の表。両方を参照している)→ `members`

どちらでつなぐか Supabase(PostgREST)には決められず、エラーになった。たとえるなら、「渋谷まで」とだけ告げたのに、地下鉄の経路が 2 本あって、運転手が迷った状態。

**なぜテストで見つからなかったか**:テストでは DB の窓口を偽物に差し替えている。偽物は「こう頼まれたらこう答える」と決まっているので、**本物の DB が持つ「結合の経路が複数あると決められない」という性質**までは再現できない。偽物のテストは、自分の書いた判断ロジックを守るのには強いが、「外の世界との約束事」を確かめるには、本物に当てるしかない。

**直し方**:経路を指定した(`members!member_id(name, name_en)`、「`member_id` の列でつながる `members`」の意味)。直したあと、読み取りだけの問い合わせを本物の DB に実行し、エラーが出ず、名前が正しく結合されて返ることを確認した。

**再発を防ぐ工夫**
- 同じ曖昧さが起きうる場所を洗い出した。他の問い合わせは 1 つのテーブルの列を選ぶだけで、結合の書き方は動画の取得の 1 か所だけだった。
- 「この問い合わせは経路を指定している」ことを確かめる小さなテスト(`lib/vote-repo.test.ts`)を足した。指定を消すと、すぐ失敗する。
- 本物の DB への確認は、書き込みを伴う前に、まず読み取りだけで行う手順にした。

### 既知の限界
- 「いま open か」の確認と、投票の保存の間には、ごくわずかな隙間(ミリ秒)がある。管理者が締切にした瞬間と重なると、ぎりぎり受け付けられることがある。10 人規模の運用では実害は小さい。完全に塞ぐには、確認と保存を DB の中で 1 回で行う仕組み(DB への追加)が必要になるが、今は入れていない。

### 確認方法
cmd で次を実行する。

```
npm test
npx tsc --noEmit
npx next build
```

- `npm test`:全テストが通る(順位計算・接続部品・投票 API)。
- `npx next build`:成功し、`/api/vote` が `ƒ (Dynamic)` と表示される。
- 開発サーバー(`npx next dev`)を起動して、トークンなし・形式違いのトークンで `/api/vote` にアクセスすると、どれも 401 と同じ日本語の文が返り、`PUT` は 405 になる(DB には触れない)。

**本物の DB での確認(実施済み。承認を取ったうえで、`seminar_vote` だけに行った)**
1. 読み取りだけの確認:API が使うのと同じ問い合わせで、エラーが出ないこと。絞り込みを外して先頭 2 件を取ると、動画の持ち主の名前が正しく結合されて返ること。
2. 書き込みを伴う通し確認:K0002 の動画を一時的に open にして、23 項目を確認し、**23 件すべて OK**。
   - 状態の取得:投票中の動画なし → `current=null`。open にすると、K0001 からは「他人の動画・未送信」、K0002 本人からは `isOwn=true`。
   - 投票:K0001→K0002 に (3,4) を送信 → 再投票 (5,2) → DB には**1 件だけ、5,2 で上書き**。別の参加者(K0003)には、その投票内容が見えない。
   - 拒否:自己投票(403)、点数 6・3.5・`"3"`・インパクト 0(400)、投票中でない動画あて(409)、存在しないトークン(401)、本文に混ぜた別人の `voterId` は無視(K0003 の票は 0 件)。

   - 後始末:テストで作った投票 1 件だけを削除し、K0002 を pending に戻した。**全員 pending・投票 0 件に戻ったことを確認**。

### 初出の専門用語と一言解説
- **Route Handler**:`app/api/…/route.ts` に書く、サーバー側の窓口。ブラウザは DB ではなく、ここに頼む。
- **PostgREST**:Supabase の裏で動く、DB を HTTP で操作できるようにする部品。
- **埋め込み(embed)**:ほかのテーブルの列を、1 回の問い合わせでまとめて取る書き方。
- **上書き(upsert)**:無ければ追加、あれば更新する操作。再投票に使う。
- **HTTP ステータスコード**:サーバーの返事の種類を表す数字(200 成功、401 本人確認できない、など)。
- **ヘッダー**:通信の「封筒に書く付帯情報」。本文とは別に、トークンなどを渡せる。
- **Cache-Control: no-store**:「この返事を覚えておかないで」とブラウザや中継に伝える指示。
- **競合状態(race condition)**:2 つの操作がほぼ同時に起きて、順番によって結果が変わってしまう問題。

| 秘密の値 | 返事の中に、トークンもキーも含まれない |

### セッション2:本物のトークンで画面を開く(スマホ幅 375×812)
**トークン入りの URL を、ブラウザに一度も入れない工夫**:自分で作った「中継サーバー」(`localhost:4111`)が、「別名の URL」(例 `/v/alias-k0001`)を、メモリの上でだけ本物のトークンの URL に書き換えて、本番用サーバー(`localhost:3111`)に渡した。
- ブラウザのアドレス(=ツールの出力に毎回出る URL)には、別名しか現れない。スクリーンショットにはアドレス欄が含まれず、アプリの画面にもトークンは表示されない。
- 本物のトークンは、DB からメモリに読むだけ。ファイルにも、ログにも書かない。ログには、別名と状態コードだけが残る。
- 終了後、3 つのログファイル(本番用サーバー、中継サーバー、開発サーバー)に、トークン 10 人分・秘密キー・URL の値が**1 件も含まれていない**ことを確認した。

確認できたこと(本物の API・本物の DB):
- K0001 の別名 URL で、投票欄が出る(「織田信長 さん」、動画は「豊臣秀吉」)。最初は 2 項目とも未選択で、送信ボタンは灰色。
- 実際に点数を押して選ぶと、2 つ選ぶまで送信できず、2 つ選ぶと押せる。送信すると「✓ 送信しました」と時刻、2 つの点数(4 点、2 点)。DB に 1 件保存された。
- 「評価を変更する」で、前の点数が選ばれた状態の変更用の投票欄になる。画面の下に固定された部分は、「変更を送信する」ボタン 1 つだけ(高さ 113px)。①を 5 に変えて送信すると、5 点と 2 点になり、DB は 1 件だけ・5,2 に上書きされた。
- K0002(動画の持ち主)の別名 URL では、「あなたの動画です」が出て、ボタンもラジオボタンも 0 個。
- K0003 の別名 URL では、新規の投票欄が出て、K0001 の点数も「送信済み」の表示も見えない。
- K0001 の画面を開き直しても、送信済みの内容(5 点、2 点)と「送信済みです(00:25)」が出る(送信直後の緑の枠は出ない)。
- K0002 を closed にすると、開いていた K0001 の画面が、自動で「いま投票中の動画はありません」に変わる。

### 食い違い(確認の方法に関するもの)と原因
**起きたこと**:ページを開いた直後、画面が「読み込み中…」のまま、10 秒待っても切り替わらなかった。そのまま画面の画像(スクリーンショット)を撮ると、その直後に、最終の状態(待機中や本人確認できない)に切り替わった。

**調べたこと**
1. 中継サーバーのログと、通信の一覧では、`/api/vote` は `200` を返していた(API は動いている)。
2. 中継サーバーを通さず、本番用サーバーにダミーのトークンで直接アクセスしても、同じ症状だった(中継サーバーが原因ではない)。
3. `curl` で HTML を取ると、サーバーは **17 ミリ秒**で、画面の注記や後から流し込む部分まで含めた完全な HTML を返していた(サーバーが遅いわけではない)。
4. 画面の画像を撮ると、すぐに最終の状態になった。
5. 開発サーバーで行った前回の確認(5c)では、同じ症状は目立たなかった。

**判断**:アプリ本体や、データの食い違いではなく、**内蔵ブラウザが、画面を描画するまで(画像を撮るなどするまで)ページの更新を進めない場面がある**ためと考えられる。確認では、ページを開いたあとに画像を撮ってから、画面の文字や状態を読み取る手順にした。
**ただし、この時点では断定ではなかった。** 内蔵ブラウザ以外で、ページを開いてから「読み込み中…」が切り替わるまでの時間を、まだ見ていなかった。→ 次の「追加調査」で、本物の Edge で確かめた。

### 追加調査:本物の Edge(ヘッドレス)で、切り替わるまでの時間を測った
**やり方**(DB には触れない・追加のパッケージなし)
- 本番用ビルドのサーバーを、`127.0.0.1`(自分のパソコンの中)だけで待ち受けて起動した。
- Windows に入っている Edge を、**ヘッドレス**(画面を出さずに動かす)で起動し、遠隔操作の仕組み(CDP)につないだ。つなぐ道具は、Node.js に標準で入っている `WebSocket` だけを使った。
- ダミーのトークン(形式が違うので、API が DB を見る前に断る)のページを開き、開いてから 100 ミリ秒ごとに、画面の中身を読み取った。「サーバーの仮表示」→「部品の読み込み中」→「本人確認できませんでした」の、どの状態かを記録した。
- デスクトップ幅と、スマホ幅(375×812・タッチ操作)で、3 回ずつ行った。

**結果:6 回中 6 回、すべて切り替わった。**

| 条件 | 切り替わるまでの時間(ミリ秒) |
|---|---|
| デスクトップ幅 | 398、190、175 |
| スマホ幅(375×812・タッチ) | 148、184、163 |

- 0.5 秒後、1 秒後、2 秒後、5 秒後、10 秒後の、**どの時点でも「本人確認できませんでした」**になっていた。
- ページを開いてから `/api/vote` に要求を出すまでが約 70〜275 ミリ秒、返事(401)が届くまでが、その直後だった。
- JavaScript の例外も、コンソールの警告・エラーも、**0 件**。画面の可視状態は、すべて「表示中」。

**結論**:本物の Edge では、アプリは、**ページを開いてから約 0.15〜0.4 秒で**「読み込み中…」から切り替わる。アプリ本体やサーバー、ポーリングの開始条件、Suspense、ハイドレーションに問題はない。先の「10 秒待っても切り替わらない」は、**内蔵ブラウザが、画面を描画するまで更新を進めない場面がある**という推測が、裏づけられた。
**残っていること**:実際のスマホ(特に iPhone の Safari)での確認は、まだ。ただし、Edge(Chromium)でここまで速く切り替わるので、大きな心配はない。QR コードの完成(段階 8)の後に、実機で一度見ておく。

### この調査の後始末

- Edge の一時プロファイル(`edge-profile-…`)は、「ファイルの削除は事前に承認を取る」というルールがあるため、**削除せずに**、パソコンの一時フォルダに残してある。不要なら、あなたの判断で削除する。

### 初出の専門用語と一言解説
- **本番用ビルド(`next build` / `next start`)**:公開用に最適化したアプリを作り、その状態で動かす方法。開発用(`next dev`)より、本物に近い。
- **リバースプロキシ(中継サーバー)**:ブラウザと本物のサーバーの間に立って、通信を取り次ぐサーバー。今回は、URL の一部を書き換えるために使った。
- **別名(エイリアス)**:本物の名前(トークン)の代わりに使う、別の呼び名。
- **ハイドレーション(hydration)**:サーバーが作った静的な HTML に、ブラウザ側のプログラムが「動き」を与える処理。これが終わるまで、ボタンなどは反応しない。
- **ストリーミング**:ページを、準備のできた部分から順に、少しずつ送る方式。
- **ヘッドレス(headless)ブラウザ**:画面を出さずに、裏で動くブラウザ。自動の確認に使う。見た目は出ないが、通信や JavaScript は本物と同じように動く。
- **CDP(Chrome DevTools Protocol)**:Chrome 系のブラウザ(Edge を含む)を、プログラムから遠隔操作する共通の仕組み。開発者ツールも、これで動いている。
- **WebSocket**:ブラウザとプログラムが、つなぎっぱなしで、双方向にやりとりする通信方式。

### 動画の状態の切替表
| 操作 | 切替 |
|---|---|
| 開始 | 未放映(pending)→ 投票中(open) |
| 締切 | 投票中 → 締切(closed) |
| 再開(押し間違いの取り消し) | 締切 → 投票中 |
| 放映できない | 未放映・投票中・締切 → 放映不可(not_shown) |
| 元に戻す | 放映不可 → 未放映 |

放映不可の動画は、いきなり「開始」できない(先に「元に戻す」が要る)。`open` が同時に 2 本にならないことは、DB の部分ユニークインデックスが最後の守りで、6b で、日本語のエラー(409)に変える。

### 「締め切って次へ」の、次の動画の選び方(依頼の条件 2)
- **名簿の学籍番号順**(K0001 → K0009 → **S001 は最後**)に見て、いまの動画より**後ろにある、未放映(pending)の最初の動画**を選ぶ。
- **放映不可(not_shown)は飛ばす**。締切(closed)・投票中(open)も飛ばす。
- いまの動画より前にある未放映の動画には、**戻らない**(戻したいときは、一覧から「開始」を押す)。後ろに未放映が無ければ、「次は無い」(null)。
- 投票中の動画が無いとき(最初)は、名簿順で最初の未放映の動画。
- 並び順は、文字の部分(K → S)、数字の部分(数として:K0010 は K0009 の後)の順に比べる。入力の並びが違っても、結果は同じ。
- テスト:S001 が最後になること、入力を逆にしても同じこと、放映不可を飛ばすこと、S001 の次は無いこと、前に戻らないこと、など 11 件。

### パスワードと、セッション Cookie
- **パスワードの照合**:入力と正しいパスワードを、それぞれ SHA-256 にして同じ長さにそろえてから、`timingSafeEqual` で比べる。長さの違いや、どこまで合っているかが、応答時間から分からない。空白は取り除かない(そのまま比べる)。
- **12 文字未満**のパスワードは、ログインを断る(6b で、サーバー側に実装する)。値は表示しない。
- **セッション Cookie**:`<期限(秒)>.<乱数>.<署名>` の形。署名は、`ADMIN_PASSWORD` から作った鍵での HMAC。
  - 有効期間は **8 時間**。改ざん、期限切れ、形式違い、遠い未来の期限は、すべて無効。
  - パスワードを変えると、すべてのセッションが無効になる。Cookie の値には、パスワードは含まれない。
  - 設定:`HttpOnly`(JavaScript から読めない)、`SameSite=Strict`(別のサイトからの通信には付かない)、パスは `/`、本番(https)だけ `Secure`。

### POST の Origin の確認(依頼の条件 3)
ブラウザが付ける `Origin`(どのサイトの画面からの通信か)が、**このサイト自身か**を確かめる。比べるのは、Origin の**ホスト(ポート込み)**で、`Host` ヘッダー、または `X-Forwarded-Host`(中継サーバーが付ける「元のホスト」)と同じなら許す。

| 場合 | 結果 |
|---|---|
| 本番(https):Origin と Host が同じ | 許す |
| localhost:ポートまで同じ(例 `localhost:3000`) | 許す |
| 標準のポート(`:443`、`:80`)が Origin に書かれている | 許す(ポートを取り除いて比べる) |
| 大文字小文字の違い | 許す |
| **中継サーバーが Host を書き換えたが、`X-Forwarded-Host` を付けている**(5d のような構成) | 許す |
| **中継サーバーが Origin を取り除いた**(5d の中継サーバーの実際の動き) | 許す(Origin なし) |
| Origin が無い(ブラウザ以外の道具) | 許す |
| 別のサイト | 断る |
| 似た名前(`….vercel.app.evil.com`、`evil-….vercel.app`)、サブドメイン | 断る |
| ポート違い(localhost の別のアプリ) | 断る |
| `"null"`、読み取れない値、Host も X-Forwarded-Host も無い | 断る |
| Host を書き換えて、`X-Forwarded-Host` も付けず、Origin はそのまま | 断る(安全側。見分けがつかないため) |

http と https の違いは見ない。それは `SameSite=Strict` の Cookie が、別に守っている。

### ログインの総当たり対策(依頼の条件 1)
`LoginLimiter`(メモリ上)。時刻は引数で受け取るので、テストで確かめられる。
- **失敗したときの待ち時間**:返事の前に、1 秒、2 秒、4 秒、8 秒と倍々に待つ(8 秒で頭打ち)。
- **IP ごとの制限**:同じ IP から **15 分に 5 回**失敗すると、その IP を **10 分**止める(残り秒数つきで 429)。止めたあとは、数え直す。成功すると、その IP の失敗の記録が消える。
- **全体の制限**:全員を合わせて **15 分に 30 回**失敗すると、**全員を 10 分**止める。止めている間は、正しいパスワードでも受け付けない。成功しても、全体の失敗の数は減らない。
- **`x-forwarded-for` を偽装されても止まる**:毎回違う IP を名乗られても、IP ごとの数は 1 回ずつだが、**全体の数が 30 回に達して止まる**(テスト:100 回の偽装のうち、31 回目から止まる)。
- **メモリの使いすぎを防ぐ**:覚えておく IP は 1000 個まで。偽装した IP を大量に送られても、古いものから忘れる。
- **弱点と割り切り**
  - 記録はメモリ上なので、サーバーが再起動したり、複数台に分かれたりすると、共有・保持されない。あくまで「速度を落とす仕組み」。本当の守りは、12 文字以上の、推測できないパスワード。
  - 全体の制限は、攻撃者に 30 回失敗させられると、**本物の管理者も 10 分ログインできなくなる**。守りを優先した割り切り。

### 初出の専門用語と一言解説
- **タイミング攻撃**:応答にかかる時間の違いから、パスワードの一部を推測する攻撃。`timingSafeEqual` は、一致・不一致にかかわらず、同じ時間で比べる。
- **ハッシュ(SHA-256)**:元の文字列から、決まった長さの「指紋」を作る計算。元には戻せない。
- **HMAC(署名)**:秘密の鍵を使って作る「改ざん防止の印」。鍵を知らないと、正しい印を作れない。
- **Cookie**:ブラウザが覚えておく小さな情報。ログインの印に使う。
- **HttpOnly / SameSite / Secure**:Cookie の安全のための設定。JavaScript から読めない / 別のサイトからの通信に付けない / https のときだけ送る。
- **Origin**:ブラウザが、通信に付ける「どのサイトの画面から来たか」の情報。
- **CSRF(クロスサイト・リクエスト・フォージェリ)**:ログイン中の人のブラウザを使って、別のサイトから、勝手に操作させる攻撃。
- **ブルートフォース(総当たり)**:パスワードを、片っ端から試す攻撃。
- **レート制限**:一定時間に受け付ける回数を制限すること。

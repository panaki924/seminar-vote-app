# 説明ログ(プレゼミ生への説明用)

## 段階:テストツール vitest の導入と ERESOLVE(依存関係の衝突)の解決

### 作ったもの
- テストを実行するための道具 `vitest` を、プロジェクトに追加した。
- あわせて `@types/node` を 20 系から 24 系に更新した。
- 変更されたファイル:`package.json`、`package-lock.json`

### 使った技術
- npm(Node.js のパッケージ管理ツール)
- vitest 5.0.4(テストフレームワーク)
- @types/node 24.19.2(Node.js の型定義)

### なぜそうしたか
最初に `npm install -D vitest` を実行したところ、`ERESOLVE` というエラーで止まった。

**何がぶつかったか**

| 部品 | 求めているもの |
|---|---|
| このプロジェクト | `@types/node` は 20 系(`^20`) |
| vitest 5.0.4 | `@types/node` は 22 系、または 24 以上(`^22.0.0 \|\| >=24.0.0`) |

プロジェクトは「20 系を使う」と書いているのに、vitest は「20 系は困る」と言っている。npm は、どちらを優先するか自分では決められないので、止まってエラーを出した。

**解決方法**
1. 自分の PC の Node.js は v24.16.0 なので、型定義も同じ 24 系に揃えるのが自然だと判断した。
2. 先に `npm install -D @types/node@24` で型定義を 24 系に上げた。
3. そのあとに `npm install -D vitest` を実行した。今度は衝突せず、そのまま入った。

**やらなかったこと**
`--force` や `--legacy-peer-deps` を付ければ、エラーを無視して入れることはできる。ただし、食い違いを抱えたまま動かすことになり、あとで原因の分かりにくい不具合が出るおそれがある。そのため、食い違いそのものを直す方法を選んだ。

### 確認方法
cmd で次の 2 つを実行する。

```
npm ls vitest @types/node
npx tsc --noEmit
```

- 1 つ目:`vitest@5.0.4` と `@types/node@24.19.2` が表示され、`invalid` や `UNMET` が出ないこと。
- 2 つ目:何も表示されずに終わること(型エラーが 0 件)。

実際の結果:どちらも問題なし。

### 初出の専門用語と一言解説
- **ERESOLVE**:npm が「依存関係をどう組み合わせても、条件を満たせない」と判断したときのエラー名。
- **依存関係(dependency)**:あるパッケージが動くために必要な、別のパッケージのこと。
- **peer dependency(ピア依存)**:「このバージョンの部品と一緒に使ってね」と、パッケージが利用者側に求める条件。
- **vitest**:テストを書いて実行するための道具。順位計算が正しいかを自動で確かめるのに使う。
- **@types/node**:TypeScript に Node.js の機能を教えるための型定義。
- **devDependencies(`-D`)**:開発中だけ使い、本番では使わない部品の置き場所。
- **package-lock.json**:実際に入ったバージョンを記録するファイル。誰が入れても同じ構成になる。
- **`tsc --noEmit`**:TypeScript の型チェックだけを行い、ファイルは出力しないコマンド。

## 段階1:順位計算 `lib/ranking.ts` とテスト

### 作ったもの
- `lib/ranking.ts`:順位を計算する 2 つの関数。
  - `computeRanking(videos, votes)`:動画と票から、順位つきの一覧を作る。
  - `filterByRevealStage(ranking, stage)`:発表段階(0〜3)で見せてよい順位だけを取り出す。
- `lib/ranking.test.ts`:上の関数が正しいかを確かめる自動テスト 20 件。
- `vitest.config.mts`:テストの設定(`lib/` 内の `*.test.ts` を対象にする)。
- `package.json` に `test` スクリプトを追加(`npm test` でテストを実行)。

### 使った技術
- TypeScript(型つきの JavaScript)
- Vitest(テストツール)

### なぜそうしたか
- **純粋関数にした**:DB も画面も使わず、「入力を渡せば結果が返る」だけの形にした。DB がなくても、テストだけで正しさを確かめられるため。
- **最初に作った**:この関数がシステムの核心(ルールそのもの)で、ほかの部分はこれを呼ぶだけになるため。
- **平均の比較は割り算せず、整数で比べた**:`1/3` のような割り切れない平均は、小数にすると誤差が出て「同点のはずが同点にならない」ことがある。合計と件数の整数どうしを掛け算で比べれば、誤差が出ない。
- **同順位は標準競技順位(1,2,2,4)**:同順位が 2 人いたら、次は 3 位ではなく 4 位にする。
- **段階の絞り込みも関数にした**:見せてはいけない順位を「画面で隠す」のではなく、「関数が返さない」ようにするため。API はこの関数の結果をそのまま返せばよい。
- **3 位が存在しない場合**:該当者のいない順位は、空の一覧を持つ順位として返す。画面側が「該当者なし(同順位のため3位はいません)」と表示する。

### 確認方法
cmd で次を実行する。

```
npm test
```

`Tests 20 passed (20)` と表示されれば成功。型チェックは `npx tsc --noEmit`(何も表示されなければ成功)。

### テストが確かめていること
| 区分 | 確かめていること |
|---|---|
| 自己投票 | 自分の動画への票は集計されない / 自己投票しかない動画は順位に出ない |
| 欠席者 | 票が 1 票の動画と 3 票の動画で、合計ではなく平均で順位が決まる |
| not_shown | 放映できなかった動画は、票があっても順位に出ず、他の順位も変わらない |
| 投票なし | 投票が 1 件もない動画は順位に出ない / 票が 0 件なら空の結果 |
| 同点 | 総合点が同じならインパクト平均が高い方が上 / 完全な同点は同順位で次が飛ぶ(1,2,2,4) / 割り切れない平均でも誤差で同点が崩れない |
| 再投票 | 同じ人が同じ動画に投票し直すと新しい内容に上書きされる(順番が逆でも日時が新しい方が残る) |
| 発表段階 | 段階0は空 / 1は3位だけ / 2は3位と2位 / 3は3位・2位・1位 / 隠すべき順位が結果のどこにも含まれない / 同順位や 3 人未満では空の順位になる / 0〜3 以外はエラー |

### 初出の専門用語と一言解説
- **純粋関数**:同じ入力なら必ず同じ結果を返し、外の状態を変えない関数。電卓のようなもの。
- **ユニットテスト(単体テスト)**:小さな部品ひとつひとつを、自動で確かめるテスト。
- **標準競技順位**:同順位が出たら、その人数分だけ次の順位を飛ばす数え方(1,2,2,4)。
- **スクリプト(`scripts`)**:`package.json` に書く、コマンドの短縮名。`npm test` は `vitest run` の短縮。

## 段階2:データベースの設計図(SQL)を作る【まだ実行していない】

### 作ったもの
- `supabase/schema.sql`:テーブル 4 つ(members / videos / votes / app_state)、制約、RLS の設定。
- `supabase/seed.sql`:初期データ(名簿 10 名、動画 10 本、アプリ状態 1 行)。
- `supabase/verify.sql`:わざと不正なデータを入れて、DB が弾くかを確かめる検証。終わったら全部取り消す。

### 使った技術
- PostgreSQL(Supabase の中身のデータベース)と、その操作言語 SQL

### なぜそうしたか
- **ルールを DB にも書いた**:画面や API のチェックをすり抜けても、DB が最後に止める。自己投票・点数の範囲・open は 1 本だけ、はすべて DB の制約にした。
- **トークンは DB が作る**:`gen_random_uuid()` を 2 つつなげた 64 文字。値は SQL ファイルのどこにも書かれないので、Git にも会話にも出ない。
- **名簿は seed.sql だけで差し替え**:名前や ID はコードに書かない。動画の行は名簿から自動で作る。
- **RLS を有効にし、ポリシーは作らない**:公開キーでは何も読み書きできない。さらに保険として、公開キー系の役割(anon / authenticated)の権限そのものも取り上げた。
- **begin ... commit で囲んだ**:途中で失敗したら、全部なかったことになる。中途半端な状態が残らない。
- **verify.sql は begin ... rollback で囲んだ**:検証用データは最後に取り消されるので、本番データを汚さない。

### 確認方法
(実行は承認後。手順は下の「Supabase の画面での実行手順」を参照)
1. `schema.sql` を実行 → 「Success. No rows returned」と出る。
2. `seed.sql` を実行 → 表に `members=10, videos=10, min_token_length=64, reveal_stage=0` と出る。
3. `verify.sql` を実行 → 赤いエラーが出ず、最後の表で `verify_leftover=0, votes=0` と出る。

実行前の確認として、使い捨てのメモリ上の PostgreSQL(PGlite)で 3 つのファイルを通し、すべて成功することを確かめた。また、制約をわざと外した状態で verify.sql を流すと、`NG:` で止まる(検証が効いている)ことも確かめた。ただし本物の Supabase ではまだ実行していない。

### テーブルと制約の対応表
| テーブル | 制約 | 守っていること |
|---|---|---|
| members | 主キー id、token は一意、token は 32 文字以上 | 学籍番号の重複なし、トークンの重複・短すぎる値なし |
| videos | 主キー member_id、status は 4 種類のみ、部分ユニークインデックス | 1 人 1 本、不正な状態なし、open は同時に 1 本 |
| votes | 主キー (voter_id, target_id)、voter_id <> target_id、tech / impact は 1〜5 | 1 人 1 動画 1 票(再投票は上書き)、自己投票なし、点数の範囲 |
| app_state | id = 1 のみ、reveal_stage は 0〜3 | 行は最大 1 つ、発表段階の範囲 |

なお「投票を受け付けるのは status='open' の動画だけ」は、DB ではなく API(段階4)で守る。

### Supabase の画面での実行手順(画面の名称は変更されることがある)
> ※この手順は、次の「段階2(方式変更)」の節で置き換えた。新しいプロジェクトは作らず、既存プロジェクトの中に専用スキーマを作る。実際に行うのは、次の節の手順のほう。

1. ブラウザで supabase.com を開き、「Start your project」からサインイン(GitHub またはメール)。
2. 「New project」を押す。Organization を選び、Name に `seminar-vote` などを入力。
3. 「Database Password」は「Generate a password」で作り、パスワード管理ツールに保存する(会話には貼らない)。
4. 「Region」は「Northeast Asia (Tokyo)」を選び、「Create new project」を押す。数分待つ。
5. 左のメニューの「SQL Editor」(`>_` のアイコン)を開き、「New query」を押す。
6. VS Code などで `supabase/schema.sql` を開いて全文コピー → エディタに貼り付け → 右下の「Run」(または Ctrl+Enter)。「Success. No rows returned」と出れば成功。
7. 左のメニューの「Table Editor」を開き、4 つのテーブルがあることを確認する。
8. 「SQL Editor」で「New query」→ `seed.sql` を貼り付けて「Run」。結果の表に `members=10` などが出れば成功。
9. もう一度「New query」→ `verify.sql` を貼り付けて「Run」。赤いエラーが出ず、最後の表で `verify_leftover=0` なら合格。`NG:` で始まるエラーが出たら不合格。
10. 失敗したら、画面のエラーメッセージをそのまま教える(トークンやキーは貼らない)。

**【注意】SQL がエラーで止まったとき**
1. まず、新しいクエリに `rollback;` と **1行だけ**書いて実行する。
2. エラーメッセージを読んで原因を直す。
3. そのあとで、もとの SQL を最初から再実行する。

なぜ必要か:`schema.sql` と `seed.sql` は `begin;`(ここから 1 かたまり)で始まり、`commit;`(確定)で終わる。途中でエラーが出ると、`commit;` まで届かず、「かたまりを開いたまま、中断した状態」で止まることがある。この状態の接続では、次に実行するものが `current transaction is aborted` というエラーで拒否される。`rollback;` は「このかたまりを取り消して閉じる」という命令で、実行すると接続が元の状態に戻り、次の SQL が通るようになる。
データは `begin;` ... `commit;` のおかげで、エラーの時点で確定されていない。そのため `rollback;` を実行しても失うものはない。
たとえるなら、ノートに下書き(begin)をしている途中で間違いに気づいたとき、下書きを破って(rollback)から、白紙で書き直すイメージ。

`verify.sql` も同じ。`NG:` というエラーで止まったときは、同様に `rollback;` を実行する。

### 初出の専門用語と一言解説
- **テーブル**:表のこと。1 行が 1 件のデータ。
- **主キー(PRIMARY KEY)**:1 行を見分けるための列。重複できない。
- **外部キー(REFERENCES)**:「別の表に実在するものだけ入れてよい」という約束。
- **CHECK 制約**:入れてよい値の条件。改札機のようなもの。
- **部分ユニークインデックス**:「条件に合う行の中だけ」重複を禁止する仕組み。ここでは「open の行は 1 本だけ」。
- **RLS(行レベルセキュリティ)**:行ごとに読み書きを制限する鍵。ポリシーが無いと誰も通れない。
- **ポリシー**:RLS の「通してよい条件」の書き方。今回は作らない。
- **service_role / anon**:Supabase の役割。service_role はサーバー専用の万能キー、anon は公開キーで権限が小さい。
- **トランザクション(begin / commit / rollback)**:複数の操作を「全部成功か、全部なかったことか」にまとめる仕組み。rollback は取り消し。
- **gen_random_uuid()**:推測できないランダムな ID を作る DB の関数。
- **シード(seed)**:最初に入れておく初期データ。

## 段階2(方式変更):既存プロジェクトの中に専用スキーマ seminar_vote を作る【まだ実行していない】

### 変えた理由(無料枠の制限)
Supabase の無料プランでは、作れるプロジェクトの数に上限がある。その枠がすでに埋まっていて、このアプリのために新しいプロジェクトを作れない。
そこで、すでにあるプロジェクト(減量アプリが使っている)の中に、このアプリ専用の「引き出し」(スキーマ)`seminar_vote` を作る方式にした。

### スキーマとは(たとえ話)
1 つのデータベースを「大きな戸棚」とすると、スキーマは「引き出し」。テーブル(表)は引き出しの中の書類にあたる。
減量アプリの書類は `public` という引き出しに入っている。このアプリの書類は `seminar_vote` という別の引き出しに入れる。
引き出しが違えば、同じ名前の書類(たとえば `members`)があっても混ざらない。

### 変えたもの
| ファイル | 変更内容 |
|---|---|
| `supabase/schema.sql` | `create schema seminar_vote;` から始め、すべての名前に `seminar_vote.` を付けた。権限は service_role にだけ渡す。 |
| `supabase/seed.sql` / `supabase/verify.sql` | すべて `seminar_vote.` 付きに変更。verify には権限の確認(テスト 14〜16)を追加。 |
| `supabase/precheck.sql`(新規) | 実行前の確認用。読み取り専用で、変更は何もしない。見るのは「`seminar_vote` が未使用か」と「必要なロール(`anon` / `authenticated` / `service_role`)があるか」の 2 点だけ。`public` など他のスキーマの中身は読まない。 |
| `supabase/teardown.sql`(新規) | 後片づけ用。`drop schema seminar_vote cascade;` のみ。**今は実行しない。** |

### 権限の考え方
- **service_role にだけ**、スキーマへの入室(usage)と、4 つのテーブルの読む・追加・更新・削除(select / insert / update / delete)を渡す。
- **anon・authenticated・public(全員を表す特別な名前)には何も渡さない**。RLS を有効にし、ポリシーも作らないので、二重に鍵がかかる。
- 権限の文は、`seminar_vote` のスキーマ名とテーブル名を 1 つずつ書いて指定した。「public スキーマのテーブル全部」のような広い範囲の文は 1 つも使っていない(検索でも確認済み)。
- ※ `from public, anon, authenticated` の `public` は「全員」を表す特別な名前で、`public` スキーマ(減量アプリの引き出し)とは別物。

### リスクと対策
| リスク | 対策 |
|---|---|
| 減量アプリの `public` を壊してしまう | すべての名前に `seminar_vote.` を付ける。広い範囲を指定する文は使わない。実行前に `precheck.sql` で「`seminar_vote` が未使用か」を確認する(`public` の中身は読まない)。実行前に使い捨ての DB で、`public` が一切変わらないことを確認済み。 |
| 秘密キーは「プロジェクト全体に届くキー」なので、漏れると減量アプリのデータにも届く | キーは `.env.local` と Vercel の環境変数にだけ置く。ブラウザ・Git・会話には出さない。コードでは `schema: 'seminar_vote'` を固定し、`public` を参照するコードは書かない。公開前(段階 10)に漏れがないか確認する。詳しくは次の「キーの影響範囲」の表を参照。 |
| コードでスキーマ指定を忘れると、同名の `public.members`(減量アプリ)を読んでしまう | 接続部品(`lib/supabase.ts`)で、スキーマを `seminar_vote` に固定する(次の「段階 3 での方針」を参照)。 |
| Data API の設定を間違えて、減量アプリが動かなくなる | 「Exposed schemas」には `seminar_vote` を**追加するだけ**にして、既存の項目は消さない。変更前の画面をメモ(スクリーンショット)しておく。 |
| 無料枠の容量・接続数を減量アプリと共有する | このアプリのデータは数十行で、10 人が 2〜3 秒おきに確認する程度。負荷は小さい。 |
| 無料プランでは自動バックアップがない場合がある | 心配なら、実行前に減量アプリ側のデータを書き出しておく(するかどうかはあなたの判断)。 |
| 使い終わったあとにデータが残る | `teardown.sql` で `seminar_vote` だけを丸ごと消せる。10/22 の後に、あなたの判断で実行する。 |

### キーの影響範囲
このアプリは、サーバー専用の秘密キー(新しい形式の `sb_secret_…` キー)を使う。環境変数の名前は `SUPABASE_SERVICE_ROLE_KEY` から **`SUPABASE_SECRET_KEY`** に変更した(`.env.local` と Vercel の両方で、この名前にそろえる)。

| 項目 | 内容 |
|---|---|
| 専用の secret key を作っても権限は変わらない | 権限は `service_role` と同じ。**減量アプリの `public` にも届く。** 「専用のキー」にしても、アクセスできる範囲が狭くなるわけではない。 |
| 範囲を守っているのは何か | キーではなく、**コードの書き方**。接続部品で `schema: 'seminar_vote'` を固定し、`public` を参照するコードを書かないこと。 |
| 専用キーの利点 | **このアプリのキーだけを、10/22 の後に単独で削除できる。** 減量アプリが使っているキーには影響しない。 |
| 削除するときの注意 | 削除は**取り消せない**。先に、「そのキーを使っている別のものが無い」「代わりのキーが不要である」ことを確認してから行う。 |
| 扱い方 | `.env.local` と Vercel の環境変数にだけ置く。ブラウザ・Git・会話には出さない。 |

### Supabase の画面での手順(画面の名称は変更されることがある)
実行前に、毎回私に声をかけてください(DB の変更にあたるため)。
1. **precheck(確認)**
   1. 既存のプロジェクトを開く。左のメニューの「SQL Editor」(`>_` のアイコン)→「New query」。
   2. `supabase/precheck.sql` を全文コピーして貼り付け、「Run」を押す。
   3. 表を目で確認する。
      - `seminar_vote の状態` の行が「**未使用(OK)**」になっている。
      - (`public` など他のスキーマの中身は、この確認では読まない。)
      - `ロール` の行に `anon` / `authenticated` / `service_role` の 3 つがある。
   4. 「【注意】すでに存在する」と出たら、ここで止まって教える。
2. **schema(スキーマとテーブルを作る)**:「New query」→ `supabase/schema.sql` を貼り付けて「Run」。「Success. No rows returned」なら成功。
3. **seed(初期データを入れる)**:「New query」→ `supabase/seed.sql` を貼り付けて「Run」。結果の表に `members=10, videos=10, min_token_length=64, reveal_stage=0` と出れば成功。
4. **verify(検証)**:「New query」→ `supabase/verify.sql` を貼り付けて「Run」。赤いエラーが出ず、最後の表で `verify_leftover=0, votes=0` なら合格。`NG:` が出たら不合格。
5. **Data API に seminar_vote を公開する**(アプリのサーバーが `seminar_vote` を読み書きするために必要)
   1. 左下の「Project Settings」(歯車)→「Data API」(古い画面では「API」)を開く。
   2. 「Exposed schemas」の欄を見つける。**今ある項目(`public` など)は消さない。**変更前の画面をメモしておく。
   3. その欄に `seminar_vote` を**追加**して、「Save」を押す。
6. エラーで止まったときは、先に `rollback;` を 1 行だけ実行してから、原因を直して再実行する(前の節の【注意】を参照)。

### 段階 3 での方針(接続部品 `lib/supabase.ts`)
段階 3 で作る接続部品では、次の 2 点を必ず指定する。
- `db: { schema: 'seminar_vote' }`:何も指定しなくても `seminar_vote` の表を使うようにして、`public` を読む事故を防ぐ。
- `auth: { persistSession: false }`:サーバー側で、ログイン状態を保存しない(キーだけで動かす)。

**`sb_secret_` キーと `@supabase/supabase-js` の対応(ソースコードを読んで確認。Supabase にはまだ接続していない)**
- インストール済みのバージョンは 2.117.3。`sb_secret_` / `sb_publishable_` を「新形式のキー」として認識するコードが入っている(未知の形式のときに出す警告は出ない)。
- キーは `apikey` ヘッダーに入る。一方、ログイン中の利用者がいないとき、データベースへの通信では同じキーが `Authorization: Bearer` にも入る(Edge Functions だけは除外されている)。
- この `Authorization` への扱いを Supabase のサーバーが受け付けるかは、ソースコードを読むだけでは分からない。接続して試すまでは「対応しているはず」で、確定ではない。段階 3 で、最小限の読み取り(`seminar_vote` の 1 テーブルの件数)で試し、エラーが出たら止まって原因を調べる。

### 確認方法
(使い捨てのメモリ上の PostgreSQL「PGlite」で確認した。本物の Supabase ではまだ実行していない)
- 減量アプリの `public` を模した DB(`members` と `votes` は、あえて同じ名前)に対して、`precheck` → `schema` → `seed` → `verify` を順に実行した。
  - 実行のたびに、`public` のテーブル・列・行・権限・RLS・ポリシー・関数が**まったく変わっていない**ことを確認した。
  - `precheck.sql` は「読み取り専用の取引」の中でも成功した(書き込みが無い証拠)。表示されるのは「`seminar_vote` の状態」と「ロール」の行だけで、`public` の情報は出ない。
  - `public` が空の DB に実行すると、`public` には何も作られなかった。
  - `schema.sql` の 2 回目は `schema "seminar_vote" already exists` で止まり、何も変わらなかった。
  - `teardown.sql` を実行すると `seminar_vote` だけが消え、`public` は変わらなかった。
- 制約や権限をわざと崩すと、`verify.sql` が `NG:` で止まることを 8 パターンで確認した。
  - 自己投票の CHECK を外す / open の一意インデックスを外す / RLS を無効のままにする
  - anon に読み取り権限を渡す / 全員(PUBLIC)にスキーマの利用権限を渡す / authenticated に書き込み権限を渡す
  - service_role への権限を渡し忘れる / トークンの CHECK を外す

### 初出の専門用語と一言解説
- **スキーマ(schema)**:データベースの中の「引き出し」。同じ名前のテーブルでも、引き出しが違えば別物。
- **public スキーマ**:Supabase が最初から用意している標準の引き出し。減量アプリはここを使っている。
- **PUBLIC(全員)**:権限の世界での「誰でも」を表す特別な名前。`public` スキーマとは別物。
- **grant / revoke**:権限を渡す / 取り上げる命令。
- **Data API / Exposed schemas**:アプリのサーバーが Supabase の表にアクセスするための窓口と、そこから見せてよい引き出しの一覧。
- **drop schema ... cascade**:引き出しを、中のテーブルごと完全に削除する命令。元に戻せない。
- **読み取り専用(read only)**:見るだけで、書き込みができない状態。precheck がこれにあたる。
